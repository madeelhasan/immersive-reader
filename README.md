# Immersive Reader

A cross-platform Flutter app that will eventually teach German through progressive word replacement while reading English documents. Opens TXT, DOCX, EPUB, PDF, and HTML files, extracts and reflows their text into a clean, paginated reading view. Full product spec and locked architecture decisions live in [`spec/SPEC.md`](spec/SPEC.md); the app itself is in [`app/immersive_reader/`](app/immersive_reader/). New to the app and just want to know how to use it? See [`app/immersive_reader/WALKTHROUGH.md`](app/immersive_reader/WALKTHROUGH.md).

This README doubles as a case study: this project was built primarily through AI coding agents (Claude Code, Qwen Code CLI, and Aider — first against a local model, later against DeepSeek's hosted API), with a human directing scope, reviewing output, and making architecture calls. The sections below document what that actually looked like in practice — including where it went wrong.

## Status

**Phase 1** (a working reflowed reader, no translation logic yet) is complete: all four formats parse correctly, adjustable font size, light/dark/system theme, persisted per-document scroll position, and EPUB chapter navigation are all implemented and verified. **Phase 2** (vocabulary dataset + flat-rate word replacement gated by a reader-declared CEFR level + tap-to-toggle UI, per `spec/SPEC.md` section 6 — deliberately not the depth/word-status adaptive algorithm from section 4.2, that's Phase 4) is functionally complete on the engine/UI side, and is where the AI-delegation setup below actually started working reliably. The vocabulary dataset is at **1,719 of the ~1,500–2,000-entry, A1–B2 target** (460 A1, 406 A2, 407 B1, 446 B2) — all four levels are now at or near their share of that target. The CEFR range itself was extended beyond spec to `A1–C2` (adding C1/C2 as a smaller top-up, not held to the same per-level volume), and the reader's level now also **advances automatically** once every word eligible at the current level reaches "learned" status, not just via the manual selector (`spec/SPEC.md` section 4.3). **Phase 3** (`backend/`, a FastAPI service) is backend-complete: it serves the vocabulary dataset, authenticates users (JWT), and syncs per-user word progress, all tested; the Flutter client currently only calls the vocabulary endpoint (falling back to its bundled copy when the backend isn't running), since auth/progress-sync wiring ties into Phase 4's client-side tracking UI.

Beyond the phased spec, the reading experience has also grown: an inline live progress bar (tap or drag to seek), in-document search (Ctrl+F, including multi-word phrase matching), a chapter-list bottom sheet, a Ctrl+G go-to-page shortcut, multi-bookmark support (with an optional auto-advancing "current position" bookmark and an Undo snackbar), a warm book-like light/dark theme (Georgia serif, cream/charcoal palettes instead of stock Material blue/white) in a readable-width column, long-press-to-hear German pronunciation via the OS's built-in TTS voices (offline, no per-word audio assets), and a local cache of parsed documents so reopening a previously-read file skips re-parsing.

`flutter analyze` is clean, the full test suite (141 tests) passes against real fixture files, and it builds and runs on Windows. Phases 4–5 (spaced-repetition progress tracking, mobile) are the current frontier — see `spec/SPEC.md` sections 5–6 for the phased scope.

## Architecture, briefly

Every input format is parsed into a common `DocumentModel` (document → paragraphs → sentences → tokens), which a single `ReaderView` renders regardless of source format. Parser details, the data flow, and the non-obvious constraints that shaped the code are documented in [`app/immersive_reader/PROJECT_OVERVIEW.md`](app/immersive_reader/PROJECT_OVERVIEW.md) and [`app/CLAUDE.md`](app/CLAUDE.md).

## Building this with AI agents: what actually happened

The point of documenting this isn't "AI wrote the app" — it's what the actual workflow looked like, including the failures, since that's the part most AI-coding writeups skip.

**Bugs found during the initial build-out.** An early pass at the parser layer had ended up with duplicate, incompatible `Token` and `DocumentParser` type definitions scattered across the codebase (multiple classes with the same name, different shapes), which produced 35 analyzer errors. Fixing it required actually tracing which definitions were live versus dead, not just silencing errors.

**A performance bug that looked like a parsing bug.** Opening a real ~130,000-word PDF appeared to "not extract any text" — the app just sat blank. The actual cause: the whole book was being tokenized into a single paragraph, and the reader view tried to build one `Wrap` containing 130,000+ individual `Text` widgets in a single frame, which hung the UI rather than erroring. The fix — capping paragraph size and routing every parser through one shared chunking function — was verified against the real file, not a synthetic test string, which is what surfaced the bug in the first place.

**A real dependency conflict, not a made-up one.** `syncfusion_flutter_pdf` (PDF text extraction) and the more "obvious" DOCX/EPUB libraries (`docx_to_text`, `epubx`) pin incompatible major versions of the `xml` package. Rather than forcing an override that silently breaks one side, DOCX/EPUB parsing was rewritten to unzip and regex the underlying XML directly — a case of the "recommended" library not being viable and the fallback approach (spec'd as an explicit alternative) being the correct call.

**Delegating to a second agent — and it broke the app.** To test whether cheaper local models could offload implementation work, Qwen (via Qwen Code CLI) was tasked with adding scroll-position persistence. Its output didn't compile: import paths that don't exist in Dart's package resolution (`package:x/lib/...`), a missing dependency it never added to `pubspec.yaml`, calls to functions that were never defined, and it silently deleted the working file-picker integration in the process. Catching this required actually reading the diff and running `flutter analyze`, not trusting a "done" report.

**A real Python packaging bug, diagnosed rather than worked around blindly.** Installing Aider (a second delegation path) failed identically in two different environments with a `BackendUnavailable: Cannot import 'setuptools.build_meta'` error. The actual cause: Python 3.14 was new enough that Aider's current release's `requires-python` metadata likely excludes it, so `pip`'s resolver silently fell back through the version history to a three-year-old release with hard-pinned, unbuildable dependencies — a subtle failure mode, not a broken package. The fix was a dedicated Python 3.11 virtual environment, which resolved the real, current version immediately.

**Local models weren't actually reliable, even after fixing the obvious problems.** Aider was pointed at `qwen2.5-coder:7b` via Ollama, and asked to add scroll-position persistence, then font size, then a theme toggle. All four attempts produced plausible-looking Dart code in the chat response — and none of it ever applied, because the model couldn't reliably follow Aider's machine-parseable edit format (SEARCH/REPLACE diff, unified diff, or whole-file), regardless of which format was requested. A theory that Ollama's default context window (2048 tokens, silently truncating anything longer with no error) was the cause led to baking a 32k-context variant via a custom Modelfile — it didn't fix it; that attempt produced an even more incoherent diff (an invented file that doesn't exist, a duplicated method definition, `// ... existing code ...` placeholders that aren't valid Dart). A much larger model (`qwen3.6:latest`, 23GB) was tried next and failed differently and worse: it hallucinated an entire fake conversation turn — inventing a message that was never sent — and never attempted the actual task. Six attempts, two models, zero successful applies. The likely root cause: this laptop's 8GB VRAM can't fit these models without quantization or CPU offload, and format-following degrades disproportionately under that kind of compression compared to raw code quality — the ideas were usually reasonable, the structured-output discipline wasn't there. All four Phase 1 UI items ended up implemented directly after the delegation attempts failed.

## The three-layer AI setup

This is the part worth explaining on its own, since it's the actual mechanism, not just an incident log:

1. **Claude Code (this session)** is the orchestrator. It holds context across the whole project, makes scope/architecture calls, writes precise task briefs for other agents, and — critically — independently re-verifies every delegated result (`flutter analyze`/`flutter test`/`flutter build`, reading the actual diff, checking `git status` to confirm something really changed) before anything counts as done. When delegation fails, it implements the fix directly rather than shipping broken or absent output. This is the expensive-per-token layer, used for judgment, not bulk typing.
2. **Aider** is the delegation harness — the thing that turns a model's response into an actual file edit, test run, and commit. It's model-agnostic: same tool, different backend swapped in via `--model provider/name`. `.aider.conf.yml` configures it to auto-run `flutter test`/`dart analyze` and self-correct before returning control, so it's not a single unverified shot. It runs from a dedicated Python 3.11 virtual environment (`aider-venv`), because the system's Python 3.14 was too new for `aider-chat`'s dependency resolution on PyPI — pip's resolver was silently falling back to a three-year-old release instead of the current one (see above).
3. **The model behind Aider** is the swappable part, and the one that actually matters for reliability. Local Ollama models were free but not reliable enough on this hardware (see above). The current setup uses **DeepSeek's hosted API** (`deepseek/deepseek-chat`) instead — pay-as-you-go, no subscription, roughly $0.14–0.28 per million tokens, serving the full unquantized model rather than a laptop-squeezed local copy. New accounts get free trial credits; testing it cost nothing beyond a small top-up once those ran out.

Two independent safety nets sit underneath all of this regardless of which model is behind Aider: Aider's own auto-test/auto-lint loop, and a **git pre-commit hook** that re-runs `flutter analyze`/`flutter test` before allowing any commit at all — so even a misconfigured or skipped self-correction loop can't get broken code into the repo. `app/CLAUDE.md` keeps an honest record of what's actually been tried and what failed, so a future session doesn't re-run the same experiment blind.

**Switching to DeepSeek didn't work immediately either** — it took three more diagnosed process bugs before it did, and none of them were the model's fault: Aider interprets file paths in its own instructions relative to the *git root*, not wherever it's invoked from (documented in its own startup banner, easy to miss anyway — files landed outside the actual Flutter project twice before this was caught); Aider silently auto-detects chat language from the OS locale, and this machine's is German, so every instruction was quietly getting a "reply in German" system prompt injected; and the lint command (`dart analyze`) failed to resolve `package:flutter/...` when Aider pointed it at a single edited file, which sent the model into a real repeated-output loop trying to "fix" an error it had no power to fix. With those three fixed, DeepSeek applied every subsequent edit correctly on the first try, for well under a cent each. The one task class that still fails even with a capable hosted model: multi-class UI restructuring (splitting a widget into stateful pieces and threading a callback across files) — that's been implemented directly every time, delegation or not.

**A fourth process bug, found much later: creating a brand-new file is a different failure mode than editing an existing one.** Every successful DeepSeek delegation up to this point had been an *edit* to a file that already existed. Asked to *create* a new file from scratch — a Flutter widget, a JSON dataset staging file — the model got stuck reasoning in circles about how to build a SEARCH/REPLACE block against content that doesn't exist yet ("the SEARCH block must have at least one line... but the file is empty..."), or silently "succeeded" while writing literal placeholder text (`[ ... ]`) instead of real content. The `--file` CLI flag compounded this: unlike in-message paths, it resolves relative to Aider's *invocation* directory rather than the git root, and reusing the same git-root-relative path habit created the identical stray-nested-directory bug from the first bullet above — twice, well after it was supposedly a known gotcha. The fix that actually worked: pre-create an empty stub file directly (bypassing Aider entirely for that one step), then have Aider *edit* it — converts the unreliable "create" task into the reliable "edit" one, no format confusion, applies cleanly.

**A real Windows-toolchain gap that `flutter pub get` couldn't have caught.** Adding `flutter_tts` for German pronunciation resolved and built fine at the Dart-dependency level, then failed at the native CMake build step: its Windows implementation needs `nuget.exe` to fetch a native dependency, and it wasn't installed on this machine. `pub get` only resolves Dart-level package versions — it has no way to know a package's *native* build step needs a separate toolchain binary; that only surfaces when you actually try to build for the platform. Chocolatey's install hit a permissions wall needing elevation this session didn't have; winget installed it without issue, just needed its shim directory added to `PATH` for the change to take effect without restarting the shell.

**A native-plugin misclassification bug, diagnosed by reading Flutter's own source rather than guessing.** `flutter run -d windows` started failing with a CMake error claiming a `windows/` build directory didn't exist inside the `msix` package — a pure-Dart packaging CLI tool (invoked via `dart run msix:create`), not a native plugin at all. Bisecting by hand pointed at `msix`, but *why* took reading `flutter_tools`' own `platform_plugins.dart`: `msix`'s `pubspec.yaml` declares `pluginClass: none` as a legacy convention meaning "no native code," which older Flutter tooling special-cased — but the current SDK's `NativeOrDartPlugin.hasMethodChannel()` only checks `pluginClass != null`, so the literal string `"none"` (non-null) gets treated as a real native plugin. True of every published `msix` version back to the oldest, not a version-pinning problem — upgrading didn't help, and pulled in an unrelated `archive`-package version conflict besides. Fixed by vendoring a locally patched copy (one line removed) wired in via `dependency_overrides`, keeping the documented packaging workflow otherwise unchanged.

**A performance fix that measured worse than the bug it was meant to fix.** Jumping to a distant position in a document with thousands of paragraphs (via search, go-to-page, chapters, or bookmarks) took 11–14+ seconds — a genuine freeze reported directly, not inferred. The first fix attempt — repeatedly re-jumping using a self-refining scroll-extent estimate, on the theory that a single jump's *target* was simply wrong — was plausible-sounding and directly measured worse: 14+ seconds, worse than the original single-jump bug it replaced. Instrumenting frame-by-frame pump timing (not just end-to-end wall clock) pinned the real cost to a single post-jump layout pass, independent of how many times it was retried: `ListView.builder`'s `SliverList` has to synchronously build/measure a large span of off-screen content to resolve a jump far from whatever's currently realized, an architectural cost that no amount of retrying, or switching `jumpTo` vs. `animateTo`, could touch. The actual fix — switching to `scrollable_positioned_list`, an index-based scrolling package (archived, last published years ago, but still resolves and runs correctly against the current Flutter/Dart SDK) — cut the identical jump to ~200ms, confirmed with a permanent regression test at the reported scale (9,000 paragraphs) with a hard time budget, rather than trusting that it "felt faster."

**A Flutter async-scheduling subtlety masquerading as a slow parser.** Large-file imports appeared to hang before the loading spinner ever showed up. The parser itself wasn't the bottleneck — `setState()` scheduling the spinner's frame doesn't force it to paint immediately: resuming from `await file.readAsBytes()` runs as a microtask, and everything after it (zip decompression, regex extraction, tokenization) has no further yield point, so the entire parse ran to completion in that same continuation before the engine ever got a chance to paint the frame `setState()` had scheduled. The fix was one explicit `await WidgetsBinding.instance.endOfFrame` between scheduling the spinner and starting the parse.

**"Just use an existing word list" had a real licensing trap underneath it.** Asked whether pre-built CEFR-graded German vocabulary lists could replace generating new ones, the two most relevant results on GitHub both turned out to be unsafe on inspection: one claimed an MIT license on the repo while its actual content was PDFs scraped from Facebook/Telegram/WhatsApp groups, referencing commercial textbooks by name — a license the repo owner had no standing to grant over content they didn't create. The other was genuinely CC BY-NC (blocks commercial use) and likely itself derived from Goethe-Institut's own regulated exam materials. The one legitimately clean option found — a frequency-ranked word list transparently derived from the open OpenSubtitles corpus — turned out to have no CEFR tags or translations at all once actually fetched and read, so it narrows the problem (which words are worth adding next) rather than replacing the existing DeepSeek-based generation step.

**Independent re-verification stayed necessary even with the "solved" DeepSeek setup.** Twice more this session, well after the process bugs above were fixed, Aider's own internal auto-test step got stuck in an unproductive loop *after* a correct edit had already been applied and committed — burning time arguing with itself over an unrelated test-command detail. The actual code changes were fine both times; the process only stayed reliable because the real diff was checked directly (`git diff`, an independent `flutter analyze`/`flutter test` run) rather than trusting Aider's own status output, and the stuck process was killed outright rather than left running. The lesson from the very first DeepSeek fixes — verify independently, don't trust a "done" report — turned out to still apply after "done" reports got trustworthy on the happy path.

## Running it

```
cd app/immersive_reader
flutter pub get
flutter analyze
flutter test
flutter run -d windows
```

`flutter` needs to be on your PATH, or invoked by full path — see `app/CLAUDE.md` for details specific to this setup.
