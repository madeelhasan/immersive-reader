# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Flutter desktop app (`immersive_reader/`) that will eventually teach German through progressive word replacement while reading English documents, plus a FastAPI backend (`../backend/`, Phase 3) serving the vocabulary dataset and syncing progress. `../spec/SPEC.md` is the source of truth for product scope and locked architecture decisions (section 2) — read it before proposing architecture changes; the intro explicitly asks agents to "propose changes here first if something doesn't fit" rather than improvise.

Phase 1 (SPEC.md section 5) is functionally complete: a clean reflowed reader for TXT/DOCX/EPUB/PDF, adjustable font size, light/dark/system theme, persisted per-document scroll position, and EPUB chapter navigation. Phase 2 (SPEC.md section 6: vocabulary dataset + tap-to-toggle UI + flat-rate random replacement gated by a reader-declared CEFR level) is functionally complete on the engine/UI side - a starter vocabulary dataset, an isolated `ReplacementEngine` with the section 4.1 level filter, and tap-to-toggle rendering in `ReaderView` are all in place. The vocabulary dataset is at 1,460 of the ~1,500-2,000 entries across A1-B2 SPEC.md 3.2 calls for (460 A1, 406 A2, 148 B1, 446 B2) - A1/A2/B2 are at or near their share of that target, B1 is the one level still meaningfully behind. Phase 3 (`../backend/`) is backend-complete: `GET /vocabulary`, real JWT auth (`POST /auth/register`/`login`), and token-protected `/progress` sync all exist and are tested. Client-side, only vocabulary-fetching is wired up (`VocabularyRepository` tries the API first, falls back to the bundled JSON) - the client doesn't register/login or sync progress yet, since that's tied to Phase 4's client-side progress-tracking UI, not Phase 3's server-side plumbing. Beyond the phased spec, the reader has also grown an inline progress bar, a Ctrl+G go-to-page shortcut, multi-bookmark support with an optional auto-advancing bookmark + undo, a warm Georgia-serif light/dark theme in a readable-width column, and long-press-to-hear German pronunciation via `TtsService` (flutter_tts, OS-native voices, offline).

**Phase 4 (SPEC.md section 4.2, SM-2 progress tracking) is now in progress** - not finished, but no longer off-limits. What exists: `Sm2Scheduler` (`lib/progress/sm2_scheduler.dart`, pure Dart) implements a concrete simplified-SM-2 algorithm - SPEC.md 3.3/4.2 only sketch the shape ("simplified SM-2 schedule based on ease_factor and exposures", "configurable curve"), so the exact numbers (ease-factor deltas of ±0.2/+0.15 clamped to [1.3, 2.8], status thresholds at 3/6 exposures) were designed and locked in as part of building this, not pulled from the spec verbatim - treat them as the working default, not gospel. `WordProgressRepository` (`lib/progress/word_progress_repository.dart`) persists that state via `LocalDb` (`lib/storage/local_db.dart` - its `word_progress` table schema has existed since the original Phase 1 skeleton commit but was dead code, never queried, until this phase), keyed by a device-local placeholder UUID (`lib/progress/local_user_id.dart`, `SharedPreferences` key `local_user_id`) standing in for real accounts until Phase 3's client-side login exists. `ReplacementEngine.selectReplacementsWithProgress()` implements SPEC.md 4.2's depth/status multipliers as a second method alongside the original flat-rate `selectReplacements` (which stays untouched/still used) - a depth multiplier ramping 5%→40% across the document, and a word-status multiplier where `learned` words get a flat 85% regardless of depth (deliberately not literally `depth * status_weight` as SPEC.md 4.2's formula reads; that formula can't actually produce "flat ~80-90% regardless of depth" through multiplication alone - the behavioral requirement was treated as the real intent over the literal formula). `ReaderView` now fires real exposure/toggle events into a `WordProgressRepository` injected from `HomePage` (constructor-optional, same DI pattern as `ttsService` - null means "don't track," which is what tests get and what a failed `LocalDb.init()` degrades to). **Not yet wired:** `HomePage` still calls the old flat-rate `selectReplacements`, not `selectReplacementsWithProgress` - the depth/status logic exists and is tested but isn't consuming real progress data into the actual replacement decision yet. Client-side Phase 3 auth/progress-sync (see above) is still untouched. Phase 5 (mobile) is still out of scope.

## Commands

All commands run from `immersive_reader/`. `flutter` is not on PATH in this environment — use the full path `C:\src\flutter\bin\flutter.bat` (or `& "C:\src\flutter\bin\flutter.bat" <cmd>` in PowerShell).

`flutter build windows`/`flutter run -d windows` need `nuget.exe` on PATH (`flutter_tts`'s Windows CMake build fetches a native dependency through it) — `flutter pub get` succeeding does NOT mean this is satisfied, since it only resolves Dart-level versions, not native toolchain requirements. Installed via winget in this environment (`winget install --id Microsoft.NuGet -e`); its shim lives at `%LOCALAPPDATA%\Microsoft\WinGet\Links\nuget.exe`, which needs adding to PATH for a shell session that predates the install (a shell restart normally isn't needed for new sessions going forward, only for the one active when it was installed).

```
flutter pub get
flutter analyze                          # must stay at 0 errors/warnings
flutter test                             # full suite
flutter test test/smoke_test.dart        # single test file
flutter build windows --debug
flutter run -d windows
```

A git pre-commit hook (`.git/hooks/pre-commit`, repo root) runs `flutter analyze` + `flutter test` automatically and blocks the commit on real errors (it parses analyzer output for `error -` lines specifically, since `flutter analyze`'s exit code also goes non-zero for info-level lints that are intentionally accepted — see below).

## Architecture

**Data flow:** `ParserRegistry.forFileName(path)` (`lib/parsers/parser_registry.dart`) picks a `DocumentParser` subclass by extension → `parser.parse(File)` returns a `DocumentModel` → `main.dart`'s `HomePage` hands that to `ReaderView(document, controller)` → rendered as a lazily-built `ListView.builder`.

**The 300-word paragraph cap is load-bearing.** Every parser ends by calling `DocumentParser.buildParagraphs(blocks)` (shared base class, `lib/parsers/parser_interface.dart`), which tokenizes each raw text block and caps paragraphs at `maxParagraphWords` (300). This exists because an earlier version dumped whole documents into one paragraph, and `ReaderView` tried to build a single `Wrap` of 130,000+ `Text` widgets in one `ListView` item, which hung the UI (looked like "no text" was extracted, but the real problem was rendering, not parsing). Any parser change must keep routing through `buildParagraphs`, not tokenize a whole document directly.

**DOCX/EPUB are parsed manually (unzip + regex over the XML), not via `docx_to_text`/`epubx`.** `syncfusion_flutter_pdf` (PDF text extraction) pins `xml ^7.x` transitively; `docx_to_text` and `epubx` both pin `xml ^6.x` — mutually incompatible in one dependency graph. Check for this class of transitive conflict (`flutter pub get` immediately) before adding any new package.

**Data model field naming is intentionally inconsistent.** `DocumentModel`/`ParagraphModel`/`SentenceModel` fields (`document_id`, `paragraph_id`, `sentence_id`) are snake_case to mirror SPEC.md section 3.1's JSON shape exactly; `Token` fields are camelCase (Dart convention). This is a deliberate, already-discussed tradeoff — don't "fix" the resulting `non_constant_identifier_names` lint infos.

**Widget tests that parse real files must use `tester.runAsync()`.** Awaiting real file I/O directly inside `testWidgets()`'s fake-async zone can hang indefinitely rather than erroring — see `test/reader_view_fixture_test.dart` for the working pattern.

**Real file fixtures live in `test/fixtures/`** (a novel-length PDF, a DOCX CV) and are exercised by `test/fixtures_check_test.dart` — prefer these over only synthetic test strings; that's what originally surfaced the paragraph-cap bug. The PDF/DOCX themselves are git-ignored (copyright/PII); only `test/fixtures/README.md` is tracked. There's no EPUB fixture on disk (none was supplied); `test/epub_chapter_test.dart` builds a minimal synthetic EPUB in-memory via the `archive` package instead.

**`DocumentModel.chapters` is optional chapter-boundary metadata, populated only by `epub_parser.dart`.** It's a `List<ChapterMarker>` (`{title, paragraphIndex}`, both in `document_model.dart`) mapping into `DocumentModel.paragraphs` — TXT/DOCX/PDF leave it empty (default `const []`). `ReaderView` only shows the chapter-nav button when it's non-empty, and jumps to a chapter by scroll-fraction approximation (`paragraphIndex / paragraphs.length`), not a pixel-exact position — deliberately, since paragraphs are capped at a fairly uniform size (see above) and exact per-item height tracking in a lazy `ListView.builder` wasn't worth the complexity for this. Chapter titles come from the first `<h1>`/`<h2>` found in each chapter's raw HTML, falling back to "Chapter N" — there's no NCX/nav.xhtml table-of-contents parsing.

**Phase 2's replacement pipeline is a straight line; Phase 4 added a second, richer path alongside it rather than replacing it.** `VocabularyRepository.load()` (`lib/vocabulary/`) reads `assets/vocab/en_de_starter.json` into a lowercase-English-keyed `Map<String, VocabularyEntry>`. `ReplacementEngine.selectReplacements()` (`lib/replacement/`, pure Dart, no Flutter imports, unit-tested with plain `Token`s per SPEC.md section 7) takes a `germanLevel` param, filters the vocabulary to entries at or below that CEFR level (cumulative - SPEC.md 4.1), and rolls a flat per-occurrence probability (level-scaled: A1 10% .. B2 25%) for each eligible word token, returning a `tokenId -> German text` map — this is still what `main.dart`'s `HomePage` actually calls. `ReplacementEngine.selectReplacementsWithProgress()` is the same eligibility filter but rolls against `probabilityFor(status, progress)` instead (SPEC.md 4.2 - depth ramps 5%→40% across the document, `learned` words get a flat 85%) - built and tested, but `HomePage` doesn't call it yet, so it has no live effect until that switch happens. `main.dart`'s `HomePage` holds the selected level (`SharedPreferences`, key `german_level`, an AppBar popup menu, default `A1`) and recomputes replacements whenever it changes. `ReaderView` renders any token present in the replacements map as German (styled blue/underlined) unless its `tokenId` is in a local `_toggledToEnglish` set, which `GestureDetector.onTap` flips — toggling is per-occurrence, not per-word, matching SPEC.md section 1 exactly. Every render of a replaced token and every tap now also fires a fire-and-forget `WordProgressRepository.recordExposure()` call (guarded by an `_exposedTokenIds` set so lazy-`ListView` rebuilds don't double-count) - real progress accumulates in the local DB starting this phase, even though nothing reads it back into the replacement decision yet.

**Phase 3 backend (`../backend/`) is a standalone FastAPI service; the Flutter client only calls its vocabulary endpoint so far.** `backend/app/main.py`'s `lifespan` creates tables and seeds the `vocabulary` table once (`backend/app/seed.py`) directly from `immersive_reader/assets/vocab/en_de_starter.json` — the Flutter asset is the single source of truth; the backend doesn't maintain a separate copy of the dataset. `GET /vocabulary` (optional `?cefr_level=` filter, unauthenticated - public read-only content) is implemented, tested, and consumed client-side by `VocabularyRepository` (`lib/vocabulary/`, tries the API with a 2s timeout, falls back to the bundled JSON on any failure). `POST /auth/register`/`login` (bcrypt hashing, `backend/app/security.py`) issue JWTs; `POST/GET /progress` (SPEC.md 3.3's `word_progress` schema) require one and derive `user_id` from it server-side rather than trusting a client-supplied value. All backend-tested (`backend/tests/`, pytest + FastAPI `TestClient`, 15 tests) and smoke-tested against a real running `uvicorn` instance. The client doesn't call `/auth` or `/progress` yet - that's Phase 4's client-side progress-tracking UI, not this phase's server-side plumbing. `JWT_SECRET_KEY` has a dev-only default that must be overridden via env var before any real deployment. Uses SQLAlchemy against SQLite by default (`DATABASE_URL` env var overrides it, matching SPEC.md section 2's SQLite→Postgres migration path) via a dedicated Python 3.11 venv (`C:\Users\adeel\backend-venv`) for the same pip-resolver-bug reason as `aider-venv` (see below).

## Delegating to other coding agents

`immersive_reader/.aider.conf.yml` configures Aider to auto-run `flutter test`/`dart analyze` and self-correct before returning control, and `PROJECT_OVERVIEW.md` is an onboarding doc written for other agents. Local Ollama models (`qwen2.5-coder:7b`, `qwen3.6:latest`) failed 6/6 times on Phase 1 work — see git history around the Phase 1 completion commits for the detail. **Switching to a hosted model (DeepSeek's API, `deepseek/deepseek-chat`) fixed reliability**, but getting there required diagnosing three separate process bugs, all still relevant to any future delegation on this repo:

- **Aider interprets in-chat/instruction file paths relative to the *git working directory*, not wherever it's invoked from.** It says so in its own startup banner every time - easy to miss. This repo's git root is one level above `immersive_reader/`. Always give Aider paths prefixed with `app/immersive_reader/...`, never bare `lib/...`, or files land outside the Flutter project entirely (this happened twice before being caught). The `--file` CLI flag is a separate case: it resolves relative to Aider's *invocation cwd*, not the git root - passing it a git-root-relative path while invoking Aider from inside `immersive_reader/` created a stray nested `immersive_reader/app/immersive_reader/...` directory once. Match the path style to whichever mechanism you're using.
- **Aider auto-detects chat language from the OS locale.** If the host machine's Windows locale isn't `en-*`, pin `chat-language: english` in `.aider.conf.yml` - otherwise Aider silently tells the model to reply in that locale's language, which measurably degrades output quality/consistency.
- **`lint-cmd`/`test-cmd` must be `flutter.bat analyze`/`flutter.bat test` with full paths, never bare `dart analyze`.** Aider invokes the lint command against a single edited file; `dart analyze <single-file>` (as opposed to `flutter analyze`, or `dart analyze` with no file argument) fails to resolve `package:flutter/...` imports for reasons specific to single-file targeting, and the model will get stuck trying to "fix" what's actually an unfixable shell/environment error - this produced a genuine repeated-output loop, not just a wrong answer.

With all three fixed, DeepSeek applied every subsequent edit correctly and cheaply (each Phase 2 module cost under a tenth of a cent). Multi-class UI restructuring (e.g. splitting a `StatelessWidget` into `StatefulWidget` + threading a callback across files, like the Phase 1 theme toggle) is still the one task class that's failed even with DeepSeek - that kind of change has consistently been implemented directly rather than delegated.

**Large single-shot edit requests (~150 JSON entries in one diff) intermittently truncate mid-response even on DeepSeek**, producing a malformed SEARCH/REPLACE block and burning all of Aider's reflection retries before giving up cleanly (no partial write - safe to just retry). Batching vocabulary-generation requests at ~75-100 entries has been reliable; larger batches aren't.

**A local model was tried for vocabulary *content* generation (not code editing) and rejected for a different reason than the earlier format-following failures.** Calling Ollama directly with structured-JSON mode (bypassing Aider's diff format entirely, so the model only had to produce valid JSON, not a machine-parseable code edit) fixed the format problem, but `qwen2.5-coder:7b` still undershot the requested count, duplicated an entry within its own output, produced UTF-8 encoding corruption in one German word, and - worse - returned two outright wrong translations (one just meant a different English word, one wasn't a real German word at all). Count/duplicate issues are exactly what the existing Python verification script already catches; translation *correctness* isn't checked by anything in the pipeline, so a wrong-but-plausible-looking entry would silently ship. Stuck with DeepSeek for vocabulary generation as a result.

**Aider silently skips editing a file that matches `.gitignore`, even when passed explicitly via `--file`.** A staging directory (`vocab_staging/`) was gitignored to stop intermediate vocab-generation files from ever being accidentally committed (see the debris-directory finding below) - which then meant Aider quietly declined to write to it at all, printing a one-line "Skipping ... that matches gitignore spec" notice easy to miss in a long log, and produced a plausible-looking chat response for an edit that was never actually applied. If a delegation target needs to live outside version control, don't gitignore its containing directory; keep the safety net as commit-time discipline (stage specific paths, review `git status` before committing) instead.

**A stray, git-tracked debris directory literally named after part of a model's own SEARCH/REPLACE reasoning text (`Let's produce the SEARCH...`) was found sitting in the repo root from an earlier session** - the `--file`-cwd-vs-git-root path bug (above) had misfiled a real, valid 75-entry B2 vocab batch into a garbage nested path, and a later broad `git add` swept the whole thing into an unrelated commit without anyone noticing. 60 of those 75 entries had never been merged into the real dataset - recovered them before deleting the debris. Lesson: after any Aider session, `git status --short` (and periodically `git log --stat` on suspicious-looking commits) is worth a real look, not just a glance - broad `git add`s can smuggle in more than expected, and it may not be pure junk.

**Even a modest single request touching 2 files can truncate mid-response** - not just the previously-documented ~150-JSON-entries scale. A 2-file, 7-change combined prompt (adding SM-2 event wiring to `ReaderView` + `HomePage`) cut off mid-edit with no error and no partial write, same as the large-batch case; splitting it into one file per delegation call fixed it. When a response looks unusually long for the task, suspect truncation before suspecting the model's judgment.

**Giving Aider a large explicit "here is everything you must not duplicate" list to manually cross-check induces a genuine repetition loop**, distinct from the format-confusion loops documented above. Asked to generate 50 new B1 words while checking each candidate against an embedded ~1,400-word avoid-list, DeepSeek got stuck repeating "X is already in list, skip" for the same handful of words hundreds of times before degenerating into unrelated garbage output and hitting Aider's reflection cap. The fix isn't a smaller list or clearer instructions - it's not asking the model to do the cross-check at all: let it generate freely from a topic brief, then dedupe/filter programmatically afterward (the established, already-reliable pattern for this dataset - see the batching note above). Reserve giving a model a literal exhaustive "don't repeat these" list for cases where that list is short.

**Aider's chat history persists across separate invocations in the same repo (`.aider.chat.history.md`) and can bleed unwanted content into a later, unrelated-looking run.** After a combined 2-file prompt truncated (see above), a follow-up run scoped to *only* one of those files ended up applying content from the earlier truncated attempt *in addition to* the new prompt's instructions, inserting the same field/method twice with two different doc comments and producing a `duplicate_definition` compile error - a bug `flutter analyze` caught immediately, but only because it was actually run. Two practical takeaways: (1) never trust a log tail snippet or a "background task completed" notification as proof of outcome - check `git log`/`git status` and read the actual resulting file, since a log file can still be mid-write when a completion notification fires; this happened twice in one session, once leading to an unnecessary retry of a task that had actually already succeeded; (2) always re-run `flutter analyze`/`flutter test` yourself after *any* delegated edit lands, even a "smaller, safer, split-up" retry - Aider's own auto-test loop isn't a substitute for independent verification.

**A real `sqflite` gotcha surfaced while building test coverage for the new `LocalDb`/`WordProgressRepository` persistence layer**: `sqflite` caches one `Database` instance per path by default (`singleInstance: true`), which silently shared state across what were meant to be separate, isolated in-memory test databases - every test that opened `sqflite_common_ffi`'s `inMemoryDatabasePath` (the literal string `:memory:`) got handed back the *same* cached connection as every other test that had opened that exact path before it, so word-progress counts accumulated across supposedly-independent test cases instead of resetting. Fixed by passing `singleInstance: false` to `openDatabase` in `LocalDb.init()` - harmless for the real app (which only ever opens one `LocalDb` anyway) and necessary for test isolation.

**A third repetition-loop trigger, distinct from the two documented above: asking Aider to make a *scoped* multi-part edit to one file - add an import here, replace two existing method bodies there, insert one brand-new method near the end there - can make DeepSeek spiral on SEARCH/REPLACE *diff mechanics* itself**, not on the code's semantics. Building `ProgressSyncService` this way produced ~3,800 lines of the model repeating variations of "does the class's closing `}` belong in the SEARCH block or the REPLACE block?" without ever emitting an edit. The first hypothesis - that uncertain phrasing in the prompt ("sqlite may hand back either int or double") was generalizing into anxious hedging about every field - was tested and falsified: removing that phrasing didn't stop the loop, it just moved to a different topic (the brace-boundary question above). The fix that actually worked: stop asking for a scoped/partial edit and instead give the complete final file content, framed explicitly as "replace the entire file, SEARCH is the current full content, REPLACE is this text verbatim." This is also what Aider chose on its own, unprompted, for the `AuthService` delegation earlier in the same session, and that one succeeded in a single fast pass - in hindsight, that was the tell. When a file's stub already has more than ~2 methods to fill in, or the edit needs to add new structure (not just fill in existing `throw UnimplementedError();` bodies), prefer whole-file replacement over a scoped diff.

**Aider's `--detect-urls` (on by default) scans the *entire* chat message for anything URL-shaped and tries to scrape it - including a URL sitting inside a pasted code block or string literal, not just prose.** A delegation prompt that pasted Dart source containing `this.baseUrl = 'http://127.0.0.1:8000'` made Aider stop and try to `Scrape http://127.0.0.1:8000...` before doing anything else; with nothing listening on that port it didn't error out cleanly, it just sat there indefinitely with no output growth (a silent stall, not a loop - the output file stopped growing entirely, which is a different failure signature to watch for than the repetition loops above). Always pass `--no-detect-urls` when a delegation prompt's pasted code contains any literal URL string.
